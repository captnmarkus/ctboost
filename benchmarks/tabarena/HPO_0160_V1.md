# CTBoost 0.1.60: frozen Lite HPO200 evaluation

This is a separately authorized evaluation of the public 0.1.60 release using
the existing baseline portfolio. It does not promote an optional learning arm
from the 0.1.59 pilot or change that pilot's admission decision. Conditional
inference feature selection and all learner defaults remain unchanged.

## Scope and selection

- All 51 TabArena-v0.1 Lite datasets, outer repeat 0 and fold 0.
- The manual default plus all 200 configurations from the original portfolio,
  including its unchanged first 25 configurations.
- Eight sequential bagging children per parent, one bagging repeat:
  **10,251 parents and 82,008 child fits**.
- Global configuration names and seeds come from the pinned TabArena generator.
  Child seeds are `configuration_index * 8 + fold_index`.
- AutoGluon Tabular 1.6.2b20260821 and TabArena integration commit
  `31026f7d758390994353eba79fbfa6747616f365` remain pinned.

No task outcomes select configurations, resources, or host assignments.
TabArena's validation predictions may select configurations and ensemble
weights for the final evaluation. Outer test predictions remain final evidence.
This is a Lite evaluation, not a TabArena-Full run or an official leaderboard
submission. No upstream pull request is updated by the run.

## Execution

Every parent receives two CPU threads, an 8 GiB memory ceiling, and a
3,600-second fit limit. A 4,500-second wall limit includes loading and cleanup.
GPU execution is disabled. Each parent retains its hardware and runtime receipt.
Timings on these different machines are not canonical TabArena timings.

Parents are ordered by global configuration index and then dataset name.
Ordinals whose remainder modulo nine is below four belong to the local PC;
the others belong to remote CPU workers. This fixes **4,556 local parents** and
**5,695 remote parents** before fitting and prevents duplicate assignments.

The local dispatcher uses up to eight workers with disjoint two-thread CPU
allocations. It reserves 4 GiB of free system RAM, initially budgets 8 GiB per
unseen dataset, and adapts admission to observed process memory. Remote workers
run at most two parents concurrently on four logical CPUs. The first remote
bundle contains one parent for transport validation; later bundles contain at
most 12. Up to five remote slots are used, subject to account capacity.

A completed parent is reused only after its result and provenance validate.
Started failures remain terminal with their diagnostics; other fixed assignments
continue. No fit is silently retried, replaced, or assigned different resources.
A future resource revision requires a separate public protocol. A pause prevents
new dispatch without discarding active work or completed results.

## Registration and evidence

Before any official fit, the machine-readable plan is committed publicly with
its complete task/configuration list, host assignments, seeds, resources, source
digests, and public release wheel URLs and SHA-256 digests. Workers verify that
immutable public plan and check the installed Python and native package files
against the approved wheel. Controller execution receipts bind the transport
code and local allocation policy as well.

Each successful result must contain all eight native child audits, the expected
seeds and baseline controls, valid predictions, and matching runtime and raw-file
digests. Failed parents and transport errors remain visible in the run state.
The final evaluation must report measured coverage and failures explicitly.
Earlier 0.1.58 and 0.1.59 artifacts are not relabeled as 0.1.60 evidence.
